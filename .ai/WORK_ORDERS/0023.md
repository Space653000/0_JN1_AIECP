# 施工單 0023 — 多分頁版面 ＋ 左右各自獨立的工作窗格（比照 Claude Code／Codex 桌面版）

**驗收方式：** `node scripts/review-gate.cjs --base <SHA> --mode fix --ci`。

## 0. 背景與擁有者要求（已確認）

擁有者現在的畫面是單一長頁面、右側欄很擠。擁有者要求：

1. 不同功能分不同頁面，不要塞在一個一直往下捲的長頁面。
2. 左右各放一個**各自獨立、可以同時做不同事**的工作窗格（不是只有排版分欄），像左邊是 Claude Code 視窗、右邊是 Codex 視窗那樣：**各自綁不同資料夾／專案、各自選 Agent、各自選模型與推理強度**，互不影響。
3. 外觀比照擁有者附的兩張 Claude Code／Codex 桌面版截圖：左側窄窄的導覽列（列出多個對話／專案），中間或右側是工作內容。

**這是本專案目前最大的一次介面架構改動，分兩個階段做，中間有一個必經的檢查點，原因見 §2。**

## 1. 規則（比照既有施工單，不重複贅述）

只走既有的安全模型（IPC 白名單、SecurityPolicy、Worker/Provider 既有機制）；不新增 shell、不放寬權限；不改 `Blueprint/`、`.github/`、`.ai/ACCEPTANCE.md`；紅測試先行、破壞紀錄、`npm run verify` 全綠、閘門 ACCEPTED（含 CI）；預設繁體中文；不寫死色碼、對比測試不得倒退；專案名稱一律 AIECP。**現有的單一工作區操作方式（今天的行為）必須繼續可用**，這是新增的模式，不是取代。

## 2. 階段一（現在就做）：把長頁面拆成真正的分頁／頁面

現況：`ui/index.html` 目前的「開始／Harness／看板／流程／目標迴圈／聯聊／證據」是同一頁面裡的分頁按鈕，切換分頁只是顯示/隱藏一段很長的內容，右側欄（本機 MCP、私人 GitHub 更新、安全橋接、備份…）永遠全部顯示，造成擁擠。

- 把右側欄目前一次全部顯示的區塊，改成跟主分頁一樣，各自有自己的入口（可以是主分頁旁再加幾個分頁，例如「供應商」「安全與備份」「更新」），一次只顯示使用者正在看的那個區塊；不要求記住所有既有的 `id`／`data-*`（但**不能刪除**，只能改變顯示邏輯與外層容器，既有測試會檢查這些選擇器）。
- 導覽方式改成比照截圖：左側是窄的導覽列（AIECP 自己的分頁清單），不是現在頂部一長排文字按鈕；小螢幕／窄欄仍要能用（沿用 0018 的 900px 以內欄寬規則）。
- 這階段不牽涉背後執行邏輯，純粹是「同一份資料，換一種顯示方式」，風險低，先做，先驗收，先合併。
- 測試：既有 UI 測試（`dashboard-visibility-ui`、`theme-behavior`、`i18n-accessibility`、`electron-shell-and-modes`、0018 的對比測試等）全部照過，不改斷言；新增測試證明每個原本的區塊仍可從新的導覽找到、一次只顯示一個分頁內容、鍵盤可達（Tab 能到達每個導覽項目）。

## 3. 階段二（先查證＋回報，等 Claude 確認做法後才寫程式）：左右各自獨立的工作窗格

這是有風險的部分，**你不要直接動手改，先做以下調查並在本檔「回報」寫下你的發現與建議，我看過再決定要不要繼續、用哪種做法**：

- 查證現況：`electron/main.cjs` 的 `controlPlane`、`harnessController`、`autonomyController` 等，是否為**模組層級的單一（singleton）**物件、`getCurrentWorkspace(state)` 是否假設**同一時間只有一個工作區在用**。這決定了「左右各自獨立同時運作」在後端要付出多大成本。
- 提出至少兩種做法讓 Claude 選，各自寫清楚代價與風險：
  1. **真正雙執行環境**：後端也雙實例化（例如每個窗格各自一份 ControlPlane／Harness／目前工作區），兩邊可以同時真的各跑一個 Mission。改動範圍大，風險較高，需要新的測試涵蓋「兩邊互不干擾」（例如一邊 STOP ALL 不影響另一邊、兩邊寫檔案／worktree 不衝突）。
  2. **畫面雙窗格＋單一後端佇列**：兩個窗格各自顯示自己綁定的資料夾、自己的 Agent／模型／強度設定與自己的「打招呼」，但真正會執行的 Mission／Task 仍走同一個後端佇列（可能是依序處理，或後端本來就能處理多個工作區的任務就直接用現有佇列）。改動範圍較小，但「同時做不同事」的即時性可能較弱，需要在回報中誠實說明差異。
  3. 若你在調查中發現後端其實已經支援多工作區併行（例如已有的 Worker Registry／Workspace 綁定機制就是為多工作區設計），直接說明並提出對應做法。
- 窗格各自的內容：資料夾／專案選擇（沿用既有的「選擇資料夾」）、Agent 清單與模型／強度設定（沿用 0019–0022 已做好的 `agentSettings`／「打招呼」，不要重寫）、該窗格自己的 Harness／看板等頁面（沿用階段一做好的分頁）。
- 兩個窗格是否可以各自切換到不同的既有分頁（例如左邊看 Harness、右邊看看板）？這是次要需求，能做則做，不要為此犧牲上面的核心需求。

**在你把調查結果和建議寫進本檔回報、狀態改成 `NEEDS-REVIEW`（不是 `DONE-PENDING-REVIEW`）之前，不要開始寫階段二的程式。** 我看過後會補一份「階段二實作指示」回這張單子或開新單子。
