## 2. 施工項 A — 單 Worker smoke 加獨立檔案 verifier

檔案：`scripts/provider-environment-verify.cjs`（及其測試）。參考現有 `multi-codex` / `opencode-ollama` 模式如何做「確定性檔案驗證」，讓 `codex-official`、`codex-pega`、`local-command` 的 smoke 也在**隔離暫存 worktree** 中要求 worker 建立一個內容可預期的檔案，由 script（而非 worker 自述）讀檔驗證，並在 check 中新增 `fileVerifier: { path, sha256, expectedSha256Match }`（不含檔案內容）。

驗收（TESTED）：以 fixed local worker / 假 provider 的確定性測試覆蓋：檔案正確 → PASS；worker 宣稱成功但未寫檔 → FAIL；內容錯 → FAIL。既有測試維持通過。

## 3. 施工項 B — 新增 `codex-fault-isolation` mode

在 `scripts/provider-environment-verify.cjs` 與 `.github/workflows/provider-environment.yml`（mode 選項與 `tests/provider-environment-workflow.test.cjs` 的斷言同步）新增 mode `codex-fault-isolation`，行為：
1. 讀前後兩次 `codex-official` 與 `codex-pega` 的 `codexHomeSha256`。
2. 階段 (a)：PEGA 程序環境注入無效 key，預期 PEGA check = FAIL（安全 error code），同時 OFFICIAL 真實 smoke = PASS。
3. 階段 (b)：OFFICIAL 程序以無效/空的隔離 `CODEX_HOME`（僅本次暫存副本，不碰真實 home）執行，預期 OFFICIAL = FAIL，PEGA = PASS。
4. 斷言：兩個 home hash 前後不變、無靜默 fallback、Worker Registry 狀態呈現失敗方 UNAVAILABLE/UNKNOWN 而另一方 READY；整體 PASS 的定義是「預期的失敗確實發生且被隔離」。
5. 產出遵循既有 `aecp.provider-environment-evidence/v1` schema（若需新增欄位，用向後相容方式並更新 provenance 驗證與測試）。

驗收（TESTED）：用 fake provider / 注入式 runner 的確定性測試覆蓋「失敗被隔離 → PASS」與「失敗外溢（另一方也失敗或 home hash 變動）→ FAIL」；workflow 測試涵蓋新 mode。不需真實網路/憑證。
