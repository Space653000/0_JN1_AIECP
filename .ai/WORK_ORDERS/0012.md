## 2. 施工項 A — 每個 IPC 通道都有統一的參數驗證（`B04-ELECTRON-L33`）

現況：`electron/main.cjs` 的 `ipcMain.handle(...)` 通道很多，多數直接讀取 `payload` 欄位，沒有統一的 schema 驗證（例如 `control-plane:approve-delivery`）。

1. 新增 `electron/lib/ipc-validation.cjs`：提供 `validated(schema, handler)` 包裝器與一組小型驗證原語（字串長度上限、整數範圍、列舉、布林、物件形狀、拒絕多餘欄位、禁止原型污染鍵如 `__proto__`）。驗證失敗一律丟出**不含 payload 內容**的固定錯誤，並不執行 handler。
2. 為 `main.cjs` 中**每一個** `ipcMain.handle`／`ipcMain.on` 通道宣告 schema 並以包裝器註冊（無參數的通道明確宣告「無參數」）。**合法呼叫的行為與回傳值不得改變**。
3. **目錄測試（比照 0010 的通知目錄測試）：** 掃描 `main.cjs` 取得所有註冊的 IPC 通道名稱，要求每個通道都出現在 schema 表中；日後新增通道卻沒宣告 schema，測試必須失敗。
4. 針對高風險通道（`control-plane:approve-delivery`、任何核准／取消／STOP ALL／寫入類、剪貼簿、檔案／Workspace 選擇、憑證類）各加至少一個「畸形 payload 被拒且 handler 未被呼叫」的測試；`preload.cjs` 的具名方法清單需與 schema 表對得上（測試）。
5. 完成後把 `B04-ELECTRON-L33` 改為 `IMPLEMENTED`（附具名測試）。

## 3. 施工項 B — Evidence 不可變（`B21-10-03`）

現況：`electron/lib/evidence-manager.cjs` 的 `write` 可重寫同一路徑，「證據參照不可變」（Blueprint/21 §10）沒有被強制。

1. 寫入語意改為 write-once：目標已存在時，若內容 SHA-256 相同則視為冪等成功；不同則**拒絕並回報衝突**（不得覆寫）。`events.jsonl` 維持 append-only。
2. 參照（manifest／task 記錄中的 evidence ref）必須包含 `sha256`，並提供 `verifyEvidence(ref)`：重新雜湊檔案，不符則回報被竄改。
3. 現有需要「更新」的證據（例如 Worker Report 於 Verifier 後回填、Review Report 重存）改為**寫入新的、帶 iteration／版本的檔案**並讓參照指向新檔，舊檔保留；確認現有流程與測試仍成立。
4. 測試：覆寫不同內容被拒、相同內容冪等、竄改檔案後 `verifyEvidence` 失敗、回填流程產生新版本且舊版本保留。完成後 `B21-10-03` 改 `IMPLEMENTED`。

## 4. 施工項 C — Result Capsule 不得在未驗證時宣稱成功（`B21-10-08`）

現況：`electron/lib/protocol.cjs` 的 `makeResultCapsule` 可依呼叫端輸入序列化成功狀態，沒有要求確定性 Verifier 證據。

1. `makeResultCapsule` 需要明確的 `verification`（`passed` 布林與證據參照）。**只有 `verification.passed === true` 才可輸出成功狀態**；否則輸出明確的 `UNVERIFIED`（或既有的失敗狀態），並保留原因。
2. 找出所有呼叫點（Safe Bridge、Autonomy、Harness、Control Plane）逐一確認會傳入真實驗證結果；不得因此使既有正常流程變成 UNVERIFIED（需有測試證明）。
3. 測試：未提供 verification → UNVERIFIED；`passed:false` → 非成功；`passed:true` 才成功；各呼叫點的整合測試。完成後 `B21-10-08` 改 `IMPLEMENTED`。
