## 1.5 施工項 0 — 最優先：繁中 Windows 下 PowerShell 輸出編碼缺陷（實際發生中）

**現象（Claude 已重現）：** 本機（zh-TW Windows，主控台碼頁 950／Big5）只要桌面上有含中文標題的視窗（例如 Chrome），`node --test tests/windows-ui-adapter.test.cjs` 的 `Windows runner can execute the read-only top-level window enumeration` 就失敗：`SyntaxError: Unexpected token '�' … is not valid JSON`，導致 `npm run verify` 在此機器無法通過（GitHub 上的英文 runner 不受影響，所以 CI 看不出來）。**這是產品缺陷，不只是測試問題：** `electron/lib/windows-ui-adapter.cjs` 以 `spawn('powershell.exe', …)` 讀取 `ConvertTo-Json` 輸出並直接 `JSON.parse`，PowerShell 以系統 OEM 碼頁（Big5）輸出，Node 卻以 UTF-8 解碼。

**要求：**
1. 找出所有 `spawn('powershell.exe'…)`／讀取 PowerShell 輸出的地方（至少 `windows-ui-adapter.cjs`、`windows-desktop-adapter.cjs`、`authenticode.cjs`——簽章者名稱可能含非 ASCII，`main.cjs` 的 probe 也請檢視），統一做法：在送出的腳本開頭強制 `[Console]::OutputEncoding=[Text.UTF8Encoding]::new($false)`（並設定 `$OutputEncoding`），Node 端明確以 UTF-8 解碼。**不得改變任何權限、參數驗證或 deny-by-default 行為。**
2. 新增測試，**不依賴桌面上剛好有中文視窗**：注入一個回傳含中日韓字元與 emoji 名稱的假 PowerShell 輸出（或假 spawn），證明解析結果正確；另加一個在 Windows 上實際啟動含 CJK 標題的子視窗／程序的整合測試（若不可行，改用注入式並在回報說明原因）。
3. 修好後在本機（碼頁 950、Chrome 開著中文頁面）執行 `npm run verify` 必須全綠，並在回報附上「修前失敗、修後通過」的輸出摘要。

## 2. 施工項 A — 通知與真實事件對齊（D1、G7）

1. **事件目錄測試**：新增測試，掃描 `electron/lib/*.cjs` 與 `electron/main.cjs` 中所有 `event('…')`（含動態組成者，請一併處理或明列例外）取得**實際發出的事件名稱清單**，要求每個名稱都被 `NOTIFICATION_RULES` 明確分類（含明確標示為「不通知」的名單）。日後新增事件卻沒分類，測試必須失敗。
2. **修正規則**：依實際名稱重寫規則，至少：`ci.failed_rework`、`ci.failed_max_iterations`、`task.failed`、`delivery.blocked`、`mission.cancelled` 等失敗／阻擋類 → ERROR；`approval.requested` → ACTION REQUIRED；`ci.passed`、`task.accepted`、`task.finished`、`delivery.merged` → SUCCESS；重試／等待／恢復重工類（如 `task.recovery_rework`、`ci.waiting`、`task.waiting_for_lock`）→ WARNING 或 INFO（在測試中寫明理由）。刪除或修正指向**從未發出**的名稱的規則（`provider.degraded`、`task.rework`、`mission.failed`、`state.failed` 等），若要保留須先在系統中真的發出該事件。
3. **CRITICAL 必須真的可達**：在政策／安全拒絕的既有呼叫點**新增一筆事件 `policy.violation`**（只記錄：動作類別、被拒原因代碼、task／run ID，不含機密或 prompt）。**不得改變任何允許／拒絕的結果**。測試須證明：(a) 拒絕時事件被寫入事件帳本；(b) 該拒絕的最終決定與新增前完全相同；(c) 通知投影將它歸為 CRITICAL。
4. 測試改用**真實事件名稱**，不得再用自訂名稱自我印證。
5. 修正後把 `B22-11-NOTIFY` 在 `.ai/TRACEABILITY.json` 更新為 IMPLEMENTED（附上述具名測試）。

## 4. 施工項 C — 擴充稽核狀態（分類機制）

擴充 `scripts/traceability-audit.cjs` 與 `.ai/TRACEABILITY.json` schema：

- 新增 status `CONFIRMED_GAP`：**已查證確實缺失**。必填：`evidence`（`{file, line 或 symbol, 說明「此處沒有該行為」}`）、`workOrder`（`UNASSIGNED` 允許，會被列出供 Claude 排程）、`note`（缺什麼、預期改哪裡）。
- 新增 status `MANUAL`：**需人工／視覺／輔助技術驗證，無法用單元測試證明**。必填：`protocol`（指向 `.ai/ACCEPTANCE.md` 第 6 節的小節，第 6 節由 0011 建立；本單先允許引用尚未存在的節名，並在稽核中以警告列出）。
- 保留 `GAP` 的意義為「**尚未分類**」。加入 `--strict` 旗標：有任何 `GAP` 存在即失敗。**本單不要把 `--strict` 串進 `npm run verify`**（0011 完成後才啟用）。
- 規則：每個 `IMPLEMENTED` 的測試必須針對該條文；同一測試被引用超過 3 條時，稽核輸出警告並要求該測試名稱或說明列明涵蓋範圍（既有 `B22-16-*` 九條共用一測試須處理：拆測試或明列）。
- 測試：`CONFIRMED_GAP` 缺 evidence／說明 → FAIL；`MANUAL` 缺 protocol → FAIL；`--strict` 遇 GAP 失敗；共用測試超過上限產生警告。
