## 0. 每次開工前

3. **一次只做一批**（`0013-batches.md` 裡編號最小、還有 `PARTIAL` 條目的批次）。做完這批就停下來回報，不要接著做下一批。
4. 跑一次 `npm run verify`，記下測試總數。它必須先是綠的；不是綠的就停下來回報，不要修。

## 1. 硬性禁止（違反任何一條就停下來回報）

- 不改 `Blueprint/`、不改 `.github/`、不改 `electron/` 的**功能程式碼**（補測試才需要的極小測試輔助除外，並在回報說明）。
- 不放寬或刪除任何既有測試的斷言。

- 不留下任何失敗的測試。

## 2. 每一條的做法（照順序，不要跳步）

對批次表裡的每個 ID：

1. **找到行為。** 在表格「行為所在」欄的檔案裡找到實作。用 Read/Grep 讀，不要猜。
2. **判斷能不能用自動測試證明：**
   - 能 → 走第 3 步。
   - 需要真人看畫面／裝置／帳號／憑證 → 把該條改成 `MANUAL`（`ACCEPTANCE.md` 第 6 節有對應小節）或 `ENVIRONMENT`，在 `note` 寫原因，**這一條就完成了**。
   - 你讀了程式碼發現**行為其實不存在或不完整** → 改成 `CONFIRMED_GAP`，`evidence` 寫 `{file, symbol, description}` 說明「哪裡沒有這個行為」，`workOrder: "UNASSIGNED"`，`note` 寫缺什麼；**不要自己去修**，也不要寫會失敗的測試。這一條就完成了。
3. **寫一個針對該條文的測試**（放在新檔 `tests/<主題>.test.cjs`，不要塞進不相關的既有檔案）：
   - 測試名稱**以條文 ID 開頭**，例如 `B04-L129 redaction removes bearer tokens from Result Capsules`。
   - **一個測試盡量只對應一條**。若一個測試確實涵蓋多條，在矩陣該條的 `evidence` 裡加 `covers: [這幾條 ID]`。
   - **必須呼叫真正的函式／模組並斷言它的結果或副作用。**
   - **不准只用正規式比對原始碼文字**，除非該條文本身就是一個「設定值」（例如 `contextIsolation: true`）。「檔案裡有這串字」不能證明行為，原始碼文字測試在此專案已經因為這個原因被降級過兩次。
   - 不依賴網路、真實憑證、桌面上剛好開著的視窗、目前時間或亂數的偶然值。
   - 測試要跑得快（單一測試盡量 < 3 秒）。
4. **用 `npm exec -- node --test tests/你的檔案.test.cjs` 執行**，確認通過。（直接用 `node --test` 會因為 PATH 缺 npm 而讓某些測試失敗。）
5. **做破壞檢查（每一條都要）：**
   ```bash
   node scripts/sabotage-check.cjs <程式檔> "<要弄壞的那一段精確文字>" "<替換文字，可為空字串表示刪除>" tests/你的檔案.test.cjs
   ```
   - 印出 `DETECTED` 且結束碼 0 → 你的測試真的在守這個行為，繼續。
   - 印出 `NOT DETECTED`（結束碼 1）→ 你的測試太弱。**改寫測試**讓它守住行為，再檢查一次。改了兩次還不行，就把該條改成 `MANUAL`／`CONFIRMED_GAP` 並說明。
   - 結束碼 2 → 那段文字不是唯一一次出現，換一段更精確的文字。
   - 這支腳本一定會把程式檔還原；做完用 `git status` 確認沒有多出你不預期的變更。
6. **更新 `.ai/TRACEABILITY.json`** 該條：`status` 改 `IMPLEMENTED`，`evidence` 改成 `[{"file":"tests/...","kind":"test","name":"你的測試名稱（與檔案內完全一致）"}]`，刪除 `workOrder`，`note` 寫一句話說明你測了什麼。

## 3. 每批做完的收尾

1. `node scripts/traceability-audit.cjs --strict` 必須通過（任何 `GAP` 或測試名稱對不上都會失敗）。
2. `npm run verify` 必須全綠。
3. `git status` 只應有：你新增的 `tests/*.test.cjs`、`.ai/TRACEABILITY.json`（以及必要時 `package.json` 的語法檢查清單不用動）。看到其他檔案被改，先弄清楚原因。
4. Commit（英文簡短訊息，例如 `test: prove batch 3 clauses with behavior tests`），**只加你改過的檔案**，不要 `git add -A`。
5. `git push origin feat/control-plane-complete-loop`。
6. 重新產生本批的狀態摘要（見下）並在本檔最下方「回報」追加一段。**然後停下來。**

## 5. 遇到這些狀況就停下來，不要自己決定

- 需要修改功能程式碼才能讓測試通過。
- 兩條藍圖規範互相矛盾。
- 你不確定某條該標 `CONFIRMED_GAP` 還是 `IMPLEMENTED`。
- `npm run verify` 在你動手前就是紅的。
- 任何一步讓你覺得需要放寬檢查或刪除斷言。

寧可把該條標成 `CONFIRMED_GAP` 或 `MANUAL` 並說明，也不要用一個很弱的測試把它標成 `IMPLEMENTED`。

- `node scripts/traceability-audit.cjs --strict`：矩陣稽核。
