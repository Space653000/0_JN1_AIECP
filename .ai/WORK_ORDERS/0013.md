## 2. 目標與範圍

`PARTIAL` 的意思是「行為存在，但缺針對該條文的測試」。本單依**風險優先序**逐批補測試，把能被自動測試證明的轉為 `IMPLEMENTED`，不能的改標 `MANUAL`／`ENVIRONMENT`／`CONFIRMED_GAP`（附證據）。**本單不要求一次做完全部**，依序做到額度或時間為止，每批獨立 commit 與回報。

**優先序（高到低）：**
1. **信任邊界與機密：** `R1.*`、`B04-*`（如 `B04-L129` 機密不得出現在所列各處、`B04-L179` MCP bearer 不得進入 log／Result Capsule、`B04-L185` Workspace 切換與執行中 MCP 範圍、`B04-RED-*`）、`B03-L113`／`B03-L116`（憑證明文不得被讀回）。
2. **核心迴圈與復原：** `R2.*`、`R4.*`、`R5.*`、`B02-*`、`B05-*`（鎖排序、跨倉庫、worktree 衝突）、`B20-27-*`、`B14-L292`（Provider 失敗後 Workspace 完整）、`B14-L349`（RED 動作經 Goal Loop 端到端）。
3. **Provider 與 Worker：** `R3.*`、`B03-*`（換 Provider 狀態不變、私有 context 不得隱性外送、Worker 同 worktree 衝突拒絕）。
4. **其餘：** `B11-*`、`B15-*`、`B16-*`、`B01-L67` 等。

## 3. 每一條的做法

1. 讀該條 `note` 與程式碼，寫**針對該條文**的測試（斷言行為；行為被拿掉時測試必須失敗）。避免只用正規式比對原始碼文字：那只能證明「文字存在」，不是行為（Claude 在 0011 已因此降級兩條）。
2. 每個測試名稱以條文 ID 開頭（如 `B04-L129 ...`），一個測試最好只對應一條；共用時在 matrix 的 `covers` 明列。
3. 更新 `.ai/TRACEABILITY.json`：`PARTIAL` → `IMPLEMENTED`（附 `kind: "test"` 證據）；`npm run verify`（含 `--strict`）必須維持通過。
4. **每批（約 10 條）隨機取 3 條做破壞檢查**，回報結果。

## 4. 交付與回報

依批次 commit、push，**提交前 `npm run verify` 全綠**；每批更新 `.ai/STATUS.md` 與 matrix；最終在「Codex 回報」列出：各 status 統計、仍為 `PARTIAL` 的清單與各自理由、破壞檢查結果、`npm run verify` 結果、最新 HEAD 的 CI。狀態改 `DONE-PENDING-REVIEW`（若未做完，寫明進度並保持 `OPEN`）。
